# Правила работы с Git

Автор: [Eugene Strebkov / eugeneamfe](https://github.com/eugeneamfe).
Коллекция: [Amfe Agent Kit](https://github.com/eugeneamfe/amfe-agent-kit).
Лицензия: [MIT](LICENSE). При копировании сохраняй эту отметку и файл лицензии.

Эти правила применяются к любому проекту, который использует Git. Перед Git-операциями проверь корень нужного репозитория через `git rev-parse --show-toplevel` и прочитай его `AGENTS.md`. Сохраняй дополнительные ограничения проекта, включая приватность данных.

В новом пустом репозитории сначала создай пустой начальный коммит в `main`, чтобы появилась база для рабочего дерева. Это только техническая инициализация: содержимое задачи добавляй уже в отдельной ветке и её постоянном рабочем дереве. Для проектов без деплоя не считай merge подтверждением деплоя: сохрани рабочее дерево и сообщи, что условие автоматической очистки не выполнено.

## Подготовка и изоляция работы

- Перед изменениями проверь текущую ветку и состояние рабочего дерева. Сохраняй чужие правки: не выполняй `reset` или `stash` за их автора.
- Изменения делай в ветках с префиксами `fix/`, `feat/`, `docs/`, `refactor/` или `chore/`.
- Новую самостоятельную задачу начинай в отдельной ветке от `main`. Другую базовую ветку используй только по явному указанию пользователя.
- Одна задача — одна ветка, одно рабочее дерево (`git worktree`) и один постоянный каталог на время задачи. Создай их до первой правки, если подходящих ещё нет.
- Все правки, тесты, ревью и коммиты задачи выполняй в её постоянном каталоге. Не распределяй реализацию между несколькими рабочими копиями и не переключай ветку в общем каталоге, которым могут пользоваться другие задачи.
- Временные копии для сравнения с базовой версией допустимы только для проверки. Не веди в них реализацию и явно сообщай пользователю их назначение.
- В начале работы и в итоговом ответе указывай ветку и абсолютный путь каталога задачи. В итоговом ответе также указывай созданные коммиты.
- Анализ без изменений не требует новой ветки, рабочего дерева или коммита.

## Продолжение существующей задачи

- Логически связанную работу продолжай в существующей локальной ветке и её рабочем дереве, если ветка ещё не была отправлена в удалённый репозиторий и не была влита в `main`, если пользователь явно не указал иное.
- Сохраняй тот же каталог. Не создавай новое рабочее дерево для каждого этапа или сообщения.
- Совпадения затронутых файлов или модуля недостаточно, чтобы считать задачи одной работой.

## Актуальность README

- Правило действует как при разработке Amfe Agent Kit, так и в любом проекте, подключившем этот skill.
- В каждой задаче проверяй корневой README и README затронутых компонентов: skills, инструментов, модулей и других частей проекта.
- Если меняются описанные возможности, поведение, структура, установка, настройки, зависимости или примеры использования, обновляй соответствующие README в той же задаче и включай их в коммит с изменениями. Не откладывай актуализацию до отдельной задачи или выпуска.
- Описывай фактически реализованное состояние. Планируемые возможности явно отмечай как планы; проверяй актуальность команд, путей, примеров и локальных ссылок.
- Если изменение не влияет на содержание README, не вноси формальные правки: кратко объясни в итоговом отчёте, почему обновление не требуется. Отсутствие README само по себе не требует создания нового файла.

## Проверки и коммиты

- Проверь законченный блок кода или документации и передай его независимому агенту на ревью. Самопроверка не заменяет независимое ревью.
- Автор запускает тесты. Ревьюеру передаются критерии готовности, diff и результаты проверок.
- Если независимый агент недоступен, сообщи об этом до объявления готовности.
- Исправь блокирующие замечания, проверь затронутое поведение и автоматически сделай локальный коммит. Отдельного разрешения на локальный коммит не требуется.
- Количество коммитов определяй по завершённым этапам. Один цельный, проверяемый этап — один коммит. Несколько самостоятельных этапов — отдельный коммит после каждого.
- Отдельные файлы и промежуточные исправления замечаний не требуют собственных коммитов.
- Перед коммитом проверь текущую ветку, staged diff и соответствие README изменениям текущего блока. Включай только свои изменения текущего блока.
- Используй английский conventional-префикс и описание по-русски. Формат заголовка: `fix(область): описание по-русски`. Выбирай префикс по характеру изменения; длина заголовка — до 72 символов.
- Тело коммита объясняет причину и результат. Объём описания должен соответствовать сложности изменения.

## Push и merge

- Изменения попадают в `main` только через pull request.
- Push и merge выполняй только по явному поручению пользователя на соответствующее действие.
- Одобрение результата само по себе не означает разрешения на push или merge.
- Уже полученное разрешение повторно не спрашивай.
- Если поручения на push нет, сообщи о локальном коммите без обязательного вопроса «пушим?».

## Очистка после завершения

После подтверждённого merge в `main` и успешного деплоя версии с изменениями задачи автоматически удали созданные для неё локальную ветку, рабочее дерево, его каталог и временные проверочные копии.

Перед удалением убедись, что:

- Все нужные изменения вошли в `main`.
- Нет несохранённых правок или нужных локальных файлов, включая untracked и ignored.
- Рабочее дерево не используется другими задачами, агентами, процессами или запущенным сервисом.

Удаляй рабочее дерево через `git worktree remove` из другого каталога, затем удаляй локальную ветку. Не применяй принудительное удаление рабочего дерева. Не удаляй общий каталог репозитория или чужие рабочие деревья.

Если условия очистки не выполнены, сохрани оставшиеся артефакты и явно сообщи причину. В итоговом ответе укажи, что было удалено.
